# 0006. A person's answers do not feed back into the mapper

## Context

The setup screen shows every open question about a mapping at once, and the person answers them in a form. The server never learns from the answers. I expected that to be a gap: the mapper works in stages (currency, decimal separator, amounts, which payment column names which invoice, customers, dates), so an answer to an early stage could settle later ones. The natural design is a loop, one question at a time, with the proposal worked out again after each answer and the conversation kept in a checkpointed graph so it survives a closed browser.

## Decision

**I did not build the loop.** I built the part that could justify it and measured it, in commit `df26095`. An answer pins a field or setting, and the baseline works the evidence that depends on it out again from the pinned column. A chooser tries each plausible answer to each open question, re-runs the proposal, and asks the question that leaves the fewest others open. A simulated person answers every question from the generator's true mapping (`python -m recon.evaluation.question_eval --seeds 3`):

| | questions shown at once | asked one at a time | pairs that needed fewer |
|---|---|---|---|
| development | 51 | 51 | 0 |
| held out | 35 | 35 | 0 |
| stress | 382 | 382 | 0 |

The loop never saved a question. On this data only three questions are ever open: which date column of the payments, which date column of the invoices, and the invoice date format. They do not depend on each other for the true answers. The baseline already uses both files together in its first pass (amounts that agree, references that name invoices, customers that appear in both), so by the time a question is left it is one the files cannot answer: whether `03/04/2026` is March or April when every value in the sample is below the 13th, or which of two dates is the issue date when both fall in the right order. Asking again with more pinned does not add information.

**What this does not show.** The data is generated by me, and so are the styles. A real export could have two unique id-like columns on each side, or a payment file with several reference-like columns, where an answer to one question narrows another. I did not write a style to produce that, because the result would show only that I can build a case where the loop helps. If real exports show chained ambiguities, the experiment is in the history and the evaluation can be run again.

## Consequences

- Setup stays a form with at most a few questions, which is also what the numbers say it needs to be.
- No checkpointed graph or extra dependency was added for the mapping stage.
- Answers are still not stored on the server: closing the browser on the setup screen loses them. The proposal is kept, so uploading is not repeated, but the choices are made again.
